# 前缀收窄检索（2026-10-15）

## 问题

旧算法先按首码点二分定位分组，再把组内的键逐个与输入比较。STPhrases 有 49238 个键、3534 个首码点组，“发”组有 653 个键，99% 分位为 173 个。`medium` 样本平均每个输入字要做约 53 次整键比较；长文本扫过大量的大组，缓存命中率下降，每字成本约为 `medium` 的 3 倍。

## 做法

依据 I2 的码点序：前缀相同的键在表中连续，按下一个码点排序，恰好在此结束的键排在最前。

- `SortedKeyTable` 新增 `keyCodePointAt(index, offset)`：返回键在 offset 处的码点，键已结束时返回 -1（小于任何码点）。offset 用后端的原生单位：String 为 UTF-16 码元，`.sok` 为 UTF-8 字节。检索算法只有一份。
- 第一个输入码点经首码点索引得到分组；之后每个码点用两次二分把范围收窄到该位置码点相同的子范围。范围的首个键恰好在此结束，就是一次命中；最后一次命中即最长前缀，与上游 `Dict::MatchPrefix` 结果相同。代价为 O(k log g)，k 为匹配的码点数，g 为组内键数。
- `.sok` 格式不变，仍不复制。新增内存只有组起点数组，22 个词典全部加载时共 67 KiB。
- 不再使用的前缀判断与长度原语已删除。

## 验证

- 契约套件新增随机对比测试，以暴力求出的最长前缀为准，在两个后端与三端运行；对收窄逻辑植入的三种边界错误都被检出。
- golden 套件通过；`upstream-diff` 两种口径各 298848 次比对，没有差异。

## 对 `.sok` v2 的结论

收窄之后，STPhrases 上每个输入字只剩十余次单码点探针。双数组 trie 能降到每字一次状态转移，但按码点建约 0.75–1 MiB，按字节建约 1.9–2.5 MiB，而现有 22 个词典共 1.7 MiB。体积与内存都会明显增加，剩下的收益却不确定，所以 v2 暂缓（D15），等剖析表明检索仍是主要开销时再议。
