# 性能

## 现状

- **内存**：`.sok` 解码不复制词典字节，16 档的 22 个词典共约 1.7 MiB。每个词典另有一个首码点索引（STPhrases 约 8 KiB）；每个转换器另占几 KiB 到二十余 KiB（s2t 10.5 KiB，s2tw 22.1 KiB）。
- **冷启动**：新进程中建档加首次转换，JVM 上 s2t 约 66 ms、t2s 约 55 ms，与 0.2.0 相当（见 [config-cold-start.md](config-cold-start.md)）；iOS 上 s2t 约 70 ms（热点修复时测得）。
- **转换**：见下表。

## 剩余差距

- **s2* 的检索**：s2t 有 67%–75% 的时间花在逐码点收窄检索上，这是数据结构的取舍：上游用内存 trie 换速度，Sokkuri 坚持零拷贝的有序表。要再缩小差距，需要换检索结构，即 `.sok` v2（D15 暂缓，估计多占 0.75–2.5 MiB，现有词典共 1.7 MiB）。
- **Native 比 JVM 慢**：s2* 约 1.8 倍。Kotlin/Native 没有内联键探针的调用链，JIT 内联了。用 Rust 或 C++ 重写同一结构，至多补上这一部分。
- **分词档重复检索**：四个带分词的 s2* 档里，分词与第一级转换用同一个 union 检索两遍，约占这四档三分之一的时间。复用分词结果依赖配置结构，还需论证与上游逐段语义等价。

## 否决过的方案

- union 词典组把 `matchAppend` 转发给胜出的子词典：胜者要多检索一次，JVM 上 s2t 由 66.4 µs 变为 69.5 µs。
- 给小的热点函数加 `inline`：Native 快 15%–19%，JVM 慢约 6%，因为展开后挤占了 HotSpot 的内联预算。

## 怎样测量

- JVM：`./gradlew :tools:benchmark:run --args="convert --profile s2t"`。样本文本在 `tools/shared-resources/samples`：`medium`、`long` 与各档的专项样本。还有 `create`、`decode`、`inspect` 子命令。
- Native：iOS 模拟器上 release 优化的测试二进制，用临时的测量代码，benchmark 工具不覆盖。
- 上游：`./gradlew :tools:upstream-diff:run --args="bench"`。
- A/B 对比：同一台机器，每次测量一个独立进程，A 与 B 按 ABBA 交替（JVM 5 轮，Native 3 轮），取各轮中位数的中位数。
