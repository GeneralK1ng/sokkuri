# 热点剖析与修复（2026-10-16）

## 起因

2026-10-15 的上游对照显示，OpenCC 的 C++ 核心在长文本上比 Sokkuri 的 JVM 实现快 2.6–4.1 倍，iOS 上的差距约为 JVM 的两倍。本次对三种实现分别采样剖析，用对照实验量化每一项，再分八个提交修复。

## 剖析方法

同一台机器、同一份 `long` 样本。JVM 用 JFR 以 1 ms 间隔采样；Native（iOS 模拟器上 release 优化的测试二进制）与上游（`-O3` 构建的采集器）用 macOS 的 `sample` 采样。另用临时计数器统计每个输入字的检索、键探针与跳过判断次数。

## 改动前的热点

| 热点 | JVM | Native | 上游的做法 |
|---|---|---|---|
| 批量跳过的每个字都在键首字集合上二分一次 | t2tw 89%，t2s 72% | t2tw 约 70% | 8 KiB 位图，一次位测试 |
| 每次读 `by lazy` 委托 | 计入上一行 | t2tw 23%，t2s 12% | 无 |
| 每次检索先在约 3500 个首码点里二分定位分组 | s2t 的检索共 69% | 59% | 根节点一次哈希查找 |
| 键探针带校验地解码 UTF-8，用 Long 运算读偏移 | s2* 25%–35% | 约 5% | 不校验 |
| 词典组用 `for` 遍历 `List`，每次分配迭代器 | 被逃逸分析消除 | s2t 约 10% | 无 |
| 词典组走 `matchPrefix`，每次命中生成对象与字符串 | s2t 约 11% | 约 7% | 返回值的视图 |

- 检索的代价不在比较键的次数：s2t 每字平均只有 2.2 次检索、约 8 次键探针。大头是分组定位和每次探针本身的开销。
- Kotlin/Native 的线程局部访问另占 2%–8%，来自运行时本身，代码层面无法消除。
- 上游的速度部分来自内存：它把词典组展开为内存里的哈希 trie，s2t 一个转换器约占 26 MiB，s2tw 约 40 MiB；Sokkuri 的 s2t 常驻约 1.6 MiB。

## 改动

每项一个提交：

1. 词典组用数组下标遍历子词典，Native 上不再每次分配迭代器。
2. 新增 `CodePointSet`：BMP 成员存为位图，每 64 位附累计计数，求秩为常数时间；增补平面成员存为有序数组。首码点索引改用它，定位分组与 `mayStartKey` 都变为常数时间。CJK 词典的集合约 5 KiB。
3. 每一级在构建时取得词典的键首字集合，两个扫描循环共用 `BulkSkip`，跳过时不再调用词典。
4. 首码点索引随检索一起构建，不再经 `lazy` 读取。`.sok` 词典经进程级缓存只解码一次，索引也只建一次。
5. `.sok` 在加载时逐键校验 UTF-8，键探针改用不校验的 `Utf8.wellFormedCodePointAt`，偏移用 Int 读取。畸形的键在加载时报 `InvalidFormat`，而不是每次探针时降级。
6. 未匹配的片段用 `appendRange` 直接从输入写出，不经临时字符串。
7. short_circuit 组把 `matchAppend` 转给第一个命中的子词典；union 组仍用 `matchPrefix` 决定胜者，原因见 [README](README.md#否决过的方案)。
8. `BulkSkip` 引用词典的键首字集合而不复制；IDS 运算符改为先比范围再查 arity。`.sok` 词典的集合因此在进程内共享。

## 验证

- `CodePointSet` 以排序列表为参照做随机测试，覆盖字边界、平面边界与码点范围外的查询。
- `BulkSkip` 在全部 BMP 码点与增补平面抽样上与 `stopsBulkSkip` 逐一比较；随机文本上与改动前的循环逐窗口一致。
- `Utf8.isWellFormed` 与一个按 RFC 3629 字节表独立写成的参照对比。
- 新测试经变异检查：植入 39 处错误，检出 37 处，其余 2 处是等价变异。
- golden 套件三端通过；16 档两种口径的输出与改动前逐字节一致；`upstream-diff` 两种口径各 302912 次比对没有差异。

## 每个提交的收益

JVM 与 Native 各取五档的 `long`，按提交顺序交替测 3 轮。表中为相对上一个提交的倍数（JVM / Native）。JVM 单项 ±10% 以内的起伏属于进程间的正常波动。

## 代价

- 解码：索引与键的 UTF-8 校验移到加载时。热态下 STPhrases 的解码由 0.16 ms 增至 1.01 ms。新进程中建档加首次转换，JVM 上 s2t 由 64.5 ms 变为 66.3 ms，Native 上三档都在 69–71 ms 之间，增幅不超过 2%。
- 每个词典：首次查找后的常驻量反而下降，STPhrases 由 16.9 KiB 降为 8.2 KiB，因为位图比去重后的首码点数组小。
- 每个转换器：首次转换后多占的堆，s2t 由 23.3 KiB 降为 10.5 KiB，s2tw 由 37.5 KiB 降为 22.1 KiB，t2s 由 15.1 KiB 降为 3.5 KiB。

剩下的差距与否决的方案见 [README](README.md)。
